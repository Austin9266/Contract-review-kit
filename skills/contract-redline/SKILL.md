# 修订与批注落盘（合同 / 法律文书通用）

## 这个技能解决什么问题

审查判断是一回事，把判断写进 Word 文件是另一回事。后者出错的方式很固定：

- 除了该改的地方，别处的**格式、内容、编号、页眉页脚**被顺手动了；
- 客户发来的是 **.doc**，交回去变成了 .docx，或者转换过程把版式冲了；
- 修订/批注的**署名和时间**是默认值、是 UTC、是同一秒钟扎堆的一串；
- 来件本来就带着客户或对方律师的修订/批注，被顺手改写成我方署名——等于把别人的修改冒认成自己的。

所以本技能的核心不是"会改"，而是**只改该改的地方 + 交付前逐项体检，不过关就不交付**。

## 铁律（每次都适用，除非用户当次另有交代）

1. **署名**：本次新增的修订与批注，作者一律取 `配置.json` 的「署名」与「署名缩写」
   （跑 `python3 scripts/config.py` 看当前生效值；本次要换用 `--author` / `--initials` 覆盖）。
   **来件里已有的第三方修订/批注（客户、对方律师、前手）一个字都不许动**——署名、时间、内容原样保留，只在其之上叠加我方的新痕迹。prep.py 会在开头把来件既有作者列出来提醒你。
2. **时间**：`w:date` 写**北京时间的钟面值再加一个 Z**（如 `2026-08-25T14:17:00Z`），秒恒为 `:00`。
   那个 Z 是 Word 的历史包袱——它写的其实是本地钟面，显示时不换算；所以"北京时间不折算 UTC"
   与"跟 Word 写得一模一样"在这里是同一件事，**不带 Z 反而不像 Word**。
   文档声明了 w16du（Word 2023+）的，修订元素另写 `w16du:dateUtc` 放真 UTC（钟面 −8h）；没声明就不写。
   **批注**的真 UTC 不在批注元素上，而是存在 `word/commentsExtensible.xml`（`w16cex:dateUtc`，
   按 durableId 关联）——stamp.py 自动为本次新增批注补条目；来件既有的该部件与其中条目
   **绝不删除、绝不改写**（删部件不清 rels/Override 引用，Word 直接报文件损坏）。
   细节见 `references/word-fingerprints.md`（照实件校准，改脚本前先看）。
   - 用户指定了时间线 → 按指定的时间线分布。
   - 未指定 → 从**用户把文件发给你的那个时刻**起算，落在 `配置.json` 的「工作时段」内（北京时间），默认不落周末。
   - 时间在文档顺序上单调递增，按"一个段落 = 一次编辑动作"聚簇，**同一簇内共享同一个时间戳**（Word 只精确到分钟），簇间隔几分钟到二十几分钟不等。
3. **后缀**：交付文件后缀与来件**完全一致**。来件 .doc 就交 .doc（.doc 是二进制旧格式，无法直接改，必须"转 docx 改完再回转 .doc"，脚本会自动做并复检回转结果）。
4. **只改该改的地方**：正文一律用本技能脚本改（默认 `run.py --plan`），不手写 XML、不重排、不美化、不动样式表与页眉页脚、不改目录与页码（目录问题只批注，末尾统一提醒"定稿后请更新目录域"）。
5. **不过体检不交付**：C0–C7 任何一项 FAIL，都停下来修，不许把文件发出去。
   C2 挂＝有改动没被修订标记包住；C7 挂＝动到了别人的痕迹——这两条一律不硬发，改交落盘块纯文字，由人上手落。
6. **快**：整张清单一次跑完，不要一条修订跑一条命令。
7. **像 Word 亲手做的**：`w:id` 从 0 起、删除的 run 带 `w:rsidDel`、新段带 `w14:paraId`、
   `people.xml` 有作者条目、`docProps/core.xml` 的最后保存人与保存时间更新为我方
   （注意 core.xml 的 `dcterms:modified` 是**真 UTC**，和 `w:date` 的规矩相反）。
   这些 stamp.py 会自动做，依据见 `references/word-fingerprints.md`。

## 前提

修订/批注**清单必须已经定好**（哪一条、原文是什么、改成什么、批注写什么）。清单由 `contract-review-sop` 技能产出（或人工定好）。清单没定就先去定，别边改边想。

## 流程：两条路，默认走第一条

慢的从来不是脚本，是"一处修订跑一条命令"的来回次数。所以**整张清单一次跑完**：
.docx 全程约 0.5 秒，.doc 约 4 秒（多的是 LibreOffice 三次进出）。设脚本目录为 `$S`（本技能的 `scripts/`）。

### 路 A（默认）：审查意见写成《落盘块》，`oneshot.py` 一条命令跑完

审查阶段产出的是一段格式固定的《落盘块》纯文字（`@修订/@删除/@批注/@新增/@删段`，
格式见 contract-review-sop 技能的 references/落盘与体检.md）。交给 `oneshot.py`，
它一个进程做完：解析 → 逐条归一化定位、收窄修订范围、算"第几处" → 生成 plan →
批量落盘 → 署名与北京时间 → 打包 → C0–C7 体检 → 交付，并把每条的状态、候选段落、
体检结果写成 JSON 交回来。

```bash
python3 $S/oneshot.py --input "来件.docx" --inspect --json -                            # 先看来件情况
python3 $S/oneshot.py --input "来件.docx" --block 落盘块.txt --auto --dry-run --json -   # 试跑
python3 $S/oneshot.py --input "来件.docx" --block 落盘块.txt --auto \
    --start "2026-08-21T09:20" --json 报告.json --emit-block 实际落盘块.txt              # 正式跑
python3 $S/oneshot.py --input "来件.docx" --block 落盘块.txt --auto --patch 决定.json    # 把决定交回去
python3 $S/oneshot.py --input "来件.docx" --search "履约保证金"                          # 查来件真实原文
```

`--auto` ＝落不了刀的修订自动降级为批注 ＋ 高把握候选自动指认；收不住的进 JSON 的 `needs_human`。
决定用一个 `--patch` 文件一次交回：`{"3":{"kind":"note","note":"…"},"7":{"src":"更短的原文"},
"9":{"pick":{"para":132}},"11":{"skip":true}}`。uid ＝落盘块里条目的先后顺序（1 起）。
**自动降级写的批注是占位口径，交付前换成自己的话，并在回复里向经办人交代。**
拿不准的一律 `skip` 并列明——不猜着往客户文件里写。人工要自己点的，同一套代码有界面版：工具包里的「落盘台」。

### 路 B：自己写 plan.json，`run.py --plan`

落盘块搞不定的疑难件（要整体重排、结构古怪、需要精细控制每条 edit）走这条。下面第 1、2 步就是它。

### 路 B 第 1 步：写清单

把审查阶段定好的每一条写成一个条目，存成 `plan.json`：

```json
{"edits":[
 {"find":"××市仲裁委员会","replace":"××仲裁委员会","note":"修订1"},
 {"find":"并按日万分之五支付违约金","replace":"","note":"修订2 纯删除"},
 {"find":"验收合格之日起","insert_after":" 30 日内","occurrence":2},
 {"after_para":37,"insert_paragraph":"9.4 ……"},
 {"delete_para":41},
 {"comment":"提请注意：……","anchor":"甲方应在收到发票后 15 日内付款"},
 {"comment":"目录未修改，请定稿后更新目录域。","para":2}
]}
```

- `find` 是**来件原文的一小段**，支持跨 run（Word 常把一句话拆成好几个 run）；同一串出现多次用 `"occurrence": N`。
- 段落序号一律按**来件原始编号**；脚本内部会把"新增段"放到最后按序号倒序执行，序号不会串位。
- **同一个 `after_para` 要插多段就写多条**，脚本会合并成一次插入并按清单顺序排列（Word 的真实动作是在该段末尾连敲几次回车，ins 标记顺着链条往下打；早期版本把标记全堆在同一段上，会产生两个 `w:ins`、段落顺序颠倒且 C2 必挂）。
- 锚点段本身是**来件既有的插入段**（客户/对方律师/前次交付敲的回车）也能插：脚本让新段各自携带 `w:ins` 段落标记、锚点段一个字不动，拒绝修订时整链合并、可完整还原来件。
- 一处意见一个条目，别把相邻几处并成一个大替换——要能一一对上审查报告的序号。`note` 随便写，方便对账。

### 路 B 第 2 步：跑一次

```bash
# 先空跑，一次看清所有锚定问题（约 0.2 秒，不写任何文件）
python3 $S/run.py --input "来件.docx" --plan plan.json \
  --name "XX合同（修订稿）" --start "2026-08-21T09:20" --dry-run

# 全绿后正式跑：准备 → 批量落盘 → 署名与时间 → 打包体检（.doc 还会回转并复检）
python3 $S/run.py --input "来件.docx" --plan plan.json \
  --name "XX合同（修订稿）" --start "2026-08-21T09:20"
```

- `--start` 填**用户把文件发给你的那个时刻**（北京时间）。有截止要求时加 `--end "2026-08-22T17:00"`，脚本把时间压进该区间；需要落周末加 `--weekend`；工作时段不同用 `--windows "09:00-12:00,14:00-18:00"` 这样的写法覆盖。
- **务必先 dry-run**：它把全部锚定失败一次列清，比正式跑一次挂一条快得多。
- 锚定串落在来件既有的修订块里时，批注会锚在整块两侧（范围粗一点但合法）；修订则会拒绝——不要在别人的修订上叠改，先跟经办人确认。
- 锚定失败时先看真实原文：`python3 $S/wredline.py work/unpacked --grep "关键词"`（或 `--list 30 45` 看第 30–45 段）。多半是空格、全角/半角、数字与汉字之间的空格对不上。报"区间里混有图片/域代码/已有修订"的，把 `find` 缩短、分两条写。
- 中途要补一条，改 plan.json 重跑 `run.py` 即可（它每次从来件重新开始，不会叠加旧修订）。

### 单步模式（只在批量模式搞不定时用）

`run.py` 内部就是这四步，必要时可单独调用：`prep.py`（解包+记基线）→ `apply.py --plan`（批量落盘）→ `stamp.py`（署名与时间）→ `finish.py`（打包体检+回转）。逐处交互式调试可用 `wredline.py --find/--replace`、`wcomment.py --anchor/--text`，但**改完必须重跑 `stamp.py` 再 `finish.py`**，否则会留下 `PENDING` 署名。

### 体检项（finish.py，任何一项 FAIL 都不许交付）

| | 检查什么 | 为什么 |
|---|---|---|
| C0 | 交付包内**每个 XML 部件都能被解析器完整解析**、[Content_Types] 与 rels **无悬空引用**、修订 `w:id` **无本次新产生的重复** | 正则手术切坏 XML（pPr/rPr 嵌套 Change 被截断）、删部件不清引用、切分带 rPrChange 的 run 复制出重复 id——三者都会让 Word 报"文件损坏"或修订错乱；C2 的正则实现抓不到结构错误，必须真解析 |
| C1 | 除 document.xml / comments*.xml / rels / 内容类型外，所有部件与来件**逐字节相同** | 样式、编号、页眉页脚、图片、字体一个都没动 |
| C2 | **拒绝全部修订后的正文 == 来件正文** | 有改动没被修订标记包住的话，Word 里看不出来，最阴 |
| C3 | 本次新增的修订与批注作者唯一、无 PENDING 残留 | 不出现 Claude/Author/第二作者（来件既有的第三方作者允许保留） |
| C4 | 本次新增的时间与 Word 同形（北京钟面+Z、秒为 00）、在工作时段内、单调不减；`dateUtc` 正好是钟面 −8h | 时间形态不对、或把北京时间当 UTC 存了 |
| C5 | 交付后缀 == 来件后缀 | .doc 进 .doc 出 |
| C6 | 每条批注都有锚点 | 否则批注存在但 Word 里看不见 |
| C7 | **来件既有的第三方修订/批注一条不少、一字未改** | 冒认别人的修改，比格式漂移严重得多 |

来件是 .doc 时还会把 docx 回转成 .doc、再读回来复检正文/修订/批注/署名/钟面时间是否都活着。

- 复检全 PASS → 交付 `work/deliver/<name>.doc`。
- 复检有 FAIL → **不要硬发 .doc**。改交 docx 备查件，并说明：来件为 .doc 旧格式，回转会丢失修订元数据/版式，客户可自行另存为 .doc。

### 交付

`SendUserFile` 交付文件；连接了本地文件夹的用 `device_commit_files` 写回原文件夹。回复里说明**改了几处修订、几条批注、时间线区间、目录未改需定稿后更新**。

## 常见坑

- **一条修订跑一条命令** → 这是最大的时间浪费。用 `oneshot.py --block`（或 `run.py --plan`），先 `--dry-run` 再正式跑。
- **来件本来就带修订** → 这是常态（客户改过一版、对方律师批过）。stamp.py 只认本次留下的 `PENDING` 占位，不碰既有署名；C7 会逐条核对。发现 C7 挂了，说明有脚本或手工操作动了别人的痕迹，必须查清楚再交付。
- **单步模式下改完忘了重跑 stamp.py** → 文件里留着 `w:author="PENDING"`，体检 C3 会拦下；改完正文必须 stamp.py → finish.py。
- **不要用 LibreOffice/pandoc 另存整个文档**（`--convert-to docx` 只在 .doc 进出口用一次）。任何一次整篇转换都会重排格式，这正是"偶发性改动"的主要来源。
- **体检 C0 报某个部件 XML 非法（`unbound prefix` 之类）** → 是脚本在「新建部件」这条路径上
  产出了坏结构（历史上：抄命名空间时抄到了 `<?xml?>` 声明，见 references/word-fingerprints.md 第 14 条）。
  修脚本，不要手写交付件的 XML；修完跑 `python3 scripts/自检.py 某份真实来件.docx`，五个变体全 PASS 才算好。
- **不要手工 unzip/zip**：用 `finish.py`，它保证 `[Content_Types].xml` 排在包首。
- **不要删任何来件既有部件**（commentsExtensible.xml 也一样）：删部件不清理 rels 与
  [Content_Types] 的对应条目就是悬空引用，Word 报"文件损坏"、python-docx 打不开。C0 会拦。
- **WPS 来件**（客户方很常见）有两个特征，脚本已处理，改脚本时别破坏：zip 里带
  目录条目（`word/` 这类，重打包要原样保留，否则 C1 误判缺失）；正文 run 级到处是
  `w:rPrChange` 格式修订（取 rPr 必须配对计数，否则切出非法 XML；切分带 rPrChange 的
  run 会复制出重复修订 id，写回前自动去重）。详见 `references/word-fingerprints.md` 第 13 条。
- **不要给已经是本次新增的段落再叠一层删除修订**，直接改插入内容。
- 目录、页码、页眉页脚一律不改，只批注。
